# Полный аудит JobGhost 0.5.2 перед production

Дата аудита: 11 сентября 2026. Платформа проверки: Windows 11 Pro, Ryzen 5 5600G, 32 ГБ RAM, NVIDIA RTX 3060.

## Итог

Версия 0.5.2 пригодна для контролируемого пилота на текущем компьютере. Основные контуры — интерфейс, API, локальная речь на GPU, OpenAI/OpenRouter, браузерный мост, нативное окно, ручной снимок и сборка — работают и покрыты автоматическими и реальными прогонами.

Для массового production-релиза версия пока не готова. Блокируют выпуск: неподписанный установщик, ручная developer-mode установка расширения Chrome, отсутствие теста на чистой Windows VM и матрицы реальных микрофонов/loopback/Zoom/Teams/OBS, а также неоформленные политика обработки данных и согласие участников записи.

## Исправленные баги 0.5.2

1. OpenRouter больше не отправляет массив `models` длиннее трёх элементов.
2. Микрофон и системный звук больше не смешиваются в одну дорожку: у каждого собственные recorder/VAD/transcript/source label.
3. Снимок не попадает в автоматический голосовой запрос. Область и весь экран прикрепляются только вручную к следующему ручному вопросу.
4. `Ctrl+Alt+S` открывает непосредственное выделение области на рабочем столе без окна выбора источника. «Экран» отдельно снимает текущий монитор. Источник аудио не зависит от снимка.
5. Промежуточный вопросительный знак больше не разрывает длинную голосовую реплику; завершение происходит по паузе.
6. Текущий распознанный текст сразу виден в поле вопроса и может быть отправлен `Ctrl+Enter`.
7. Локальная модель использует `large-v3-turbo`, CUDA float16 и реальную пробную инференс-проверку; при невозможности CUDA есть CPU int8 fallback.
8. Названия `Node`, `FastAPI`, `Kubernetes` нормализуются только по высокоуверенным шаблонам.
9. Ответы OpenAI/OpenRouter отображаются по SSE-дельтам, а Markdown больше не показывается сырыми `**`-маркерами.
10. Скрытый чат адаптирует высоту к полному ответу, но сохраняет установленный пользователем минимальный размер.
11. Закрытие нативного тестового окна больше не оставляет поздний IPC-handler и ложную ошибку в консоли.
12. Неудачный CUDA probe больше не может оставить ложный статус «Готово»: модель публикуется только после полностью успешной проверки.
13. Compact-панель закреплена к границам viewport, а не к родительскому header/padding; ввод голоса не стирается после ответа. Длинный контент прокручивается внутри, а не обрезается за окном.
14. Роль по выбранному резюме пересобирается на каждом API-запросе, включая после перезапуска backend.
15. Письма используют выбранный OpenAI/OpenRouter, а не всегда браузер. OpenRouter получил бюджет 4096 и low reasoning; исчерпание лимита явно сообщается.
16. HH нормализует неразрывные пробелы подтверждения. Предварительная проверка не посещает response URL, неопределённый dispatch получает NEEDS_REVIEW с запретом повторов.
17. Упакованный desktop не запускает служебный Chrome при выбранном OpenAI/OpenRouter.

Дополнительный прогон: 4,66 с синтетической RU-речи → MediaRecorder WebM → точный вопрос за 912 мс. Это не проверка физического микрофона. Native region fixture и границы compact viewport прошли. Screen capture fixture после ожидания отрисовки: 22 096 байт; первоначальный ранний захват дал пустой кадр, тест ожидания исправлен.

## Реальный HH canary — неуспешная приёмка

На аккаунте владельца импортировано резюме, прочитана подходящая fullstack-вакансия, сгенерировано и проверено письмо через бесплатный OpenRouter. После перехода на URL формы HH показал «Вы откликнулись», но выбор резюме и доставку письма подтвердить не удалось. Возможен побочный эффект самого GET. Повторов и дополнительных откликов не выполняли. Локально сохранён NEEDS_REVIEW и audit event, владелец уведомлён. Это не успешный автоотклик. До нового контролируемого теста автоматический HH остаётся pilot-only; прямой переход в форме preflight удалён, начальный клик охраняется от записывающих запросов.

OpenRouter не гарантирует мгновенный ответ: генерация письма существенно дольше короткого вопроса. Не переключаем на платный провайдер без выбора пользователя.

## Оставшиеся баги и технические риски

### P0 — блокируют массовый production

1. **Установщик не подписан.** Windows SmartScreen может показать жёсткое предупреждение. Нужен EV/OV code-signing certificate и проверка подписи в CI.
2. **Расширение устанавливается вручную в developer mode.** Для обычного пользователя нужен Chrome Web Store/enterprise package с фиксированным ID и управляемым обновлением.
3. **Нет чистого E2E на новой Windows VM.** Текущий ПК уже содержит предыдущую версию, Chrome-профиль и системные зависимости. Нужны install/start/update/uninstall/reboot проверки на чистых Windows 11 23H2/24H2.
4. **Нет физической матрицы аудио.** Синтетический SAPI-файл доказывает кодирование и распознавание, но не качество конкретных USB/Bluetooth-микрофонов, echo cancellation и loopback в Zoom/Teams/Meet.
5. **Нет юридического release gate.** Нужны явное согласие на запись собеседника, политика приватности/retention, условия OpenAI/OpenRouter/HH и региональные требования.
6. **Нет production-приёмки HH.** Автотесты и защитный preflight есть, но перед общим выпуском нужен отдельный контролируемый сценарий на тестовой вакансии: CAPTCHA/допвопросы/неопределённый submit/идемпотентность.

### P1 — исправить сразу после пилота

1. `RealtimeTranscriber` не переподключает OpenAI Live после сетевого обрыва. Сейчас пользователь получает понятную ошибку, но должен перезапустить источник.
2. Web Audio использует устаревающий `ScriptProcessorNode`. Перенести ресемплинг/VAD в `AudioWorklet`, чтобы не зависеть от main thread UI.
3. Порог VAD `0.012` фиксированный. На тихом микрофоне возможен пропуск начала, на шумном — позднее завершение. Нужны 1–2 секунды автокалибровки, noise floor и видимый тест источника.
4. При одновременной речи двух людей последние partial-дельты конкурируют за одно поле ввода. Нужны две видимые live-строки и timestamp merger, не перезаписывающий второй источник.
5. CPU fallback при двух дорожках может не успевать за фрагментами; очередь ограничена, но нет автоматического увеличения fragment size или отключения менее приоритетного источника.
6. OpenAI Live создаёт отдельную платную сессию для каждого источника. Нужны счётчик времени/примерной стоимости и явное подтверждение облачной отправки аудио.
7. Установщик с GPU-моделью крупный. Нужна продуктовая схема `Core` + проверяемый optional GPU/model pack либо надёжный resumable download с SHA-256.
8. Нет встроенного автообновления, rollback и миграционного smoke перед переключением версии.
9. Нет подписанного SBOM и автоматического dependency/security scan для Python, npm, Electron и расширения в CI.
10. Локальный HTTP API защищён bind/origin/IPC, но не аутентифицирован от другого локального процесса пользователя. Нужен ephemeral session token для mutating HTTP/WS endpoints.
11. В backend-тестах 256 deprecation warnings, в основном timezone-naive `datetime.utcnow()`. Перевести модели и запросы на timezone-aware UTC до следующего обновления Python/SQLAlchemy.
12. Нет opt-in crash telemetry с редактированием PII и пользовательской кнопки «Скачать диагностический отчёт» без резюме/аудио/снимков.

### P2 — улучшения качества

1. Добавить выбор конкретного микрофона/динамика, переименование устройств и тест «я слышу себя / я слышу собеседника».
2. Добавить пользовательскую настройку паузы VAD, чувствительности и языка для каждого источника при сохранении безопасных defaults.
3. Добавить visual diff для обычного и compact UI на 100/125/150/200% Windows scaling и двух мониторах.
4. Довести keyboard-only/focus trap/контраст до WCAG 2.2 AA и проверить Narrator.
5. Вынести большой `InterviewCapture.tsx` в `useAudioCapture`, `useSpeechPipeline`, `CaptureSettings` и `TranscriptPanel`.
6. Вынести большой `ChatAnswer.tsx` в composer/session/settings/history hooks и компоненты; добавить AbortController для отмены SSE.
7. Добавить версионирование API/IPC/extension protocol и compatibility handshake при частичном обновлении.
8. Добавить benchmark corpus RU/EN с шумом и техническими терминами, WER/CER и допустимыми latency budgets.
9. Добавить лимит/индикатор размера изображения до Base64-кодирования и тест очень широких/HiDPI экранов.
10. Добавить локализованные понятные коды ошибок upstream вместо передачи части текста стороннего API.

## Критерий готовности production

Production разрешён только когда все P0 закрыты, все P1 либо закрыты, либо письменно приняты владельцем с датой, clean-VM и физическая аудиоматрица зелёные, установщик/обновление подписаны, а controlled HH canary не допускает повторного или неопределённого отклика.
